# Требования к внешней интеграции умных устройств

## 1. Общая модель взаимодействия

- **Backend**
  - Единственный источник решений по доступу
  - Владельцем и хранителем чувствительных данных (биометрические шаблоны, гос. номера)
- **Внешняя система управления устройствами**
  - Не хранит биометрию и персональные данные
  - Исполняет команды и инициирует запросы на решение
- **Умные устройства**
  - Не принимают решений самостоятельно
  - Выполняют команды, полученные от внешней системы

---

## 2. Требования к безопасности

### 2.1 Общие требования
- Все взаимодействия должны происходить по **защищённым каналам (TLS)**
- Запрещён прямой доступ:
  - внешней платформы к БД backend
  - умных устройств к backend
- Чёткое разделение доверенных зон:
  - Mobile App - Backend (user zone)
  - External Platform - Backend (system-to-system zone)

### 2.2 Защита данных
- **Биометрические данные**
  - Хранятся только в виде шаблонов
  - Не передаются во внешнюю платформу
- **Гос. номера**
  - Хранятся в backend
  - Во внешнюю платформу передаётся только результат проверки (`ALLOW / DENY / UNAVAILABLE`)
- Все чувствительные данные шифруются при хранении и не логируются в открытом виде

### 2.3 Изоляция и минимизация
- Внешняя система не имеет информации о пользователях
- Backend возвращает только минимально необходимый ответ:
  - действие (ALLOW / DENY / FALLBACK)
  - идентификатор запроса
  - TTL решения

---

## 3. Аутентификация и авторизация

### 3.1 Аутентификация между системами
- Используется **system-to-system authentication**:
  - OAuth 2.0 Client Credentials **или**
  - mTLS (в зависимости от платформы)
- Каждая внешняя система имеет уникальный `client_id` или сертификат

### 3.2 Авторизация
- Строится на принципе **scope / permissions**:
  - `access:decision.read`
  - `access:decision.request`
- Backend проверяет:
  - кто запрашивает решение
  - для каких типов устройств
  - для каких домов / шлагбаумов

### 3.3 Управление доступом
- Возможность отзыва ключей / сертификатов
- Ограничение по IP / network zone
- Поддержка **rate limiting** и защиты от повторных запросов (anti-replay)

---

## 4. Взаимодействие между системами

### 4.1 Инициатор взаимодействия
- Внешняя система инициирует запрос при событии с устройства (лицо, номер авто, кнопка)
- Backend отвечает на запрос, не инициируя действия самостоятельно

### 4.2 Формат взаимодействия
- REST / HTTPS (синхронный запрос–ответ)
- Строгий контракт API:
  - versioned API
  - схема запросов и ответов
- Идемпотентность запросов (request_id)

### 4.3 Типовой flow (решение по доступу)
1. Устройство фиксирует событие
2. Внешняя система формирует запрос в backend
3. Backend:
   - валидирует запрос
   - применяет правила доступа
4. Backend возвращает решение: `ALLOW / DENY / UNAVAILABLE`
5. Внешняя система исполняет команду и логирует результат

---

## 5. Надёжность и отказоустойчивость
- Backend может вернуть:
  - `ALLOW`
  - `DENY`
  - `UNAVAILABLE`
- Внешняя система:
  - корректно обрабатывает отказ backend
  - имеет fallback-сценарий (ручное управление, звонок)
- Таймауты и ретраи ограниченные, с backoff

---

## 6. Аудит и трассируемость
- Backend ведёт аудит всех запросов и принятых решений
- Внешняя система логирует исполнение команд
- Используются:
  - `correlation_id / request_id`
  - синхронизированное время (NTP)

---

## 7. Требования к развитию интеграции
- Версионирование API без breaking changes
- Документированный контракт (OpenAPI)
- Возможность подключения новых типов устройств и добавления новых правил доступа без изменений внешней платформы

---

## 8. Краткое резюме
Внешняя интеграция должна быть строго изолированной и безопасной:  
- Внешняя система инициирует запросы на принятие решений  
- Backend выступает как единственный источник логики и данных  
- Умные устройства выполняют команды без знания контекста  
- Аутентификация и авторизация по строгим правам  
- Все чувствительные данные остаются внутри backend
